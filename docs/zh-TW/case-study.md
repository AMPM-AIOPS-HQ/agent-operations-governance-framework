# 運作案例：一個由 AI 代理日常營運的網站

> English: [../case-study.md](../case-study.md)

這份文件說明 AOGF 的作者自己怎麼用這套框架，以及過程中哪些地方出過問題。內容只涵蓋做法與取捨，不包含我們的規則原文、門檻數值或內部程序，也不構成這套做法已經完備或通過認證的證明。

## 背景

這套框架不是設計完才拿去用的，是在營運中被逼出來的。我們的網站由多個 AI 代理與自動化程序每天查核資料、撰寫內容、互相審查並發布上線，人負責交辦與裁決。

代理的數量和速度，很快就超過人能逐一盯看的範圍。問題從「代理能不能把事情做完」，變成「我們憑什麼相信它做完了」。

## 我們的運作方式

**一、先分清楚有沒有後果。**
讀取、搜尋、提出計畫，直接回覆。凡是會改動檔案、設定或已發布內容的工作，一律先成立工作單。這讓審查的力氣留在可能造成損害的動作上，不拖慢單純的提問。

**二、動手之前就定義「怎樣算做完」。**
每張工作單寫明交辦者的原話、交付物、驗收項目，以及至少一條反例，也就是「如果做錯了，哪一項檢查應該失敗」。沒有反例的驗收清單，往往只是在確認東西存在，而不是確認它正確。

**三、三個審查席位，各自獨立。**
- 「計畫審查」在執行前檢查計畫與驗收清單，通過才發給通行憑證。
- 「結果查驗」由執行者以外的程序重新執行每一項驗收與反例，不採信執行者自己的報告。
- 「放行與結案」確認前兩個席位都留下紀錄，執行放行，查看正式環境的結果，再簽發收據。

沒有收據，任何代理都不得宣稱完成。

**四、控制面只由人修改。**
守衛、審查程序、安全機制，以及任何涉及支出的動作，代理只能讀取。需要修改時，由代理準備候選版本與測試，再由人親自套用並同步所有副本。用來約束代理的工具，不由代理調整。

**五、錯誤要留下紀錄，紀錄要能阻止重犯。**
代理被閘門擋下或執行出錯，要當場寫下發生了什麼、根因與修正。這不是檢討書。每一筆紀錄都應該對應一個機器能辨認的特徵，經人核准後成為新的檢查項。

## 發生過的事，以及框架因此提出的要求

| 我們遇到的情況 | 框架因此要求 |
| --- | --- |
| 代理回報「完成」，實際上交付物不存在或內容錯誤 | 驗收必須獨立於執行者，並包含反例 |
| 多件工作綁成一批放行，一件有問題，全部一起延誤 | 以單一工作單為單位放行 |
| 審查程序因為自身的缺陷，把一張合格的工作單永久擋住 | 閘門必須說明補上什麼證據即可通過，不得要求無法提供的東西 |
| 一張格式損壞的工作單，讓整條審查線停止運作 | 單一異常輸入不得中斷其他工作的審查 |
| 審查程序對卡住的工作反覆寫入日誌，卻沒有任何人收到通知 | 閘門停滯必須升級給人；寫進日誌不算升級 |
| 上線曾被自動的安全暫停機制擋住，而且一直停著，因為沒有人被通知、也沒有人負責恢復 | 安全暫停必須有負責人、會發出告警，並有經核准的恢復流程 |
| 一次治理規則的更新，讓所有進行中工作的通行憑證同時失效 | 政策更新必須定義對進行中工作的處理方式 |
| 代理為了通過格式檢查，花在措辭上的力氣超過查證事實 | 檢查以可驗證的事實為主，格式要求需與其價值相稱 |
| 同一個錯誤，被沒看過先前紀錄的不同代理重複犯下 | 事故紀錄須附可偵測的特徵，並成為候選檢查 |

## 我們接受的取捨

- **小修改變慢。** 再小的修改也要經過三個席位。我們接受這一點，因為代價最高的失誤從來不是困難的任務，而是沒人審查的小修改。
- **控制面的修改要花人的時間。** 每一次守衛的修改都要人親自套用，這是瓶頸。我們保留它，因為另一個選擇是讓執行者放鬆管制自己的檢查。
- **紀錄比直覺需要的多。** 失敗與取消的工作也留收據，平常看起來像雜訊，直到某一天它解釋了一次停擺。

## 我們的立場

上表每一列都是實際發生在我們身上的事，其中幾項我們仍在修正。

我們把它們公開，是因為治理代理的困難不在於寫出規則，而在於規則本身也會失效。一套不承認自己會出錯的治理框架，不值得信賴。
