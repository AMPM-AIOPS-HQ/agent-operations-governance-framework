# 使用說明

> English: [../usage-guide.md](../usage-guide.md)

這份說明帶你把框架套用到一條工作流程上。假設你已經讀過[首頁](../../README.md)。文中所有例子都是虛構的。

## 你要建立的東西

四樣，照這個順序：

1. 一條規則：**什麼時候需要工作單**（[先分類](work-order-lifecycle.md#先分類什麼時候需要工作單)）。
2. 團隊要填寫的**工作單**格式（[空白模板](../../examples/work-order.example.yaml)）。
3. **三個審查席位**，以及各由誰或什麼來擔任（[品質閘門](quality-gates.md#三個審查席位)）。
4. 每次執行結束都要產生的**收據**（[空白模板](../../examples/receipt.example.json)）。

開始時不需要新的軟體。一個共用資料夾、一份檢查清單，加上兩位不是執行者的人，就足以做第一次試行。

## 步驟一：挑一條工作流程

選一條會改動外部系統、但可以復原的流程：開合併請求、更新文件、整理工單。不要從不可逆或會花錢的事情開始。

*虛構例子：某團隊讓代理更新產品文件裡的「支援版本」表。*

## 步驟二：寫下分類規則

一句話就夠：「讀取與提案不需要工作單；凡是修改已發布的頁面就要。」把它貼在執行者看得到的地方。

## 步驟三：填一張工作單

複製空白模板，把每一欄填滿。團隊最常寫得含糊的三個欄位，剛好是最重要的三個：

| 欄位 | 寫得弱 | 寫得強 |
| --- | --- | --- |
| `scope.prohibited_actions` | 「不要弄壞東西」 | 「除了版本頁以外的頁面不得修改；不得更動導覽列」 |
| `acceptance` | 「表格已更新」 | 「每一列都與發行清單相符；若出現一個不存在的版本，這項檢查必須失敗」 |
| `stop_conditions` | 「出問題時」 | 「讀不到發行清單時停止；會變動超過五列時停止」 |

第二列示範的就是**反例**：一項在工作做錯時應該要失敗的驗收檢查。少了反例，檢查往往只證明檔案存在。

## 步驟四：指派三個席位

| 席位 | 第一次試行時可以是 |
| --- | --- |
| 計畫審查 | 一支會退回空白欄位的小程式，加上一位閱讀驗收清單的人 |
| 結果查驗 | 另一位人員或另一個程序，重新執行驗收檢查 |
| 放行與結案 | 實際發布修改、查看發布後頁面、並寫下收據的人 |

唯一不能放寬的規則：**執行者不得擔任自己工作的任何席位。**

## 步驟五：跑一次，寫下收據

執行這條流程。不論結果如何都要填收據，包含被停下或被退回的情況。記下每個席位的判定，以及任何擋住工作的事。

## 步驟六：擴大範圍之前，先讀收據

跑過十次左右，一起把收據讀一遍。留意：

- 從來不會失敗的檢查。它可能什麼都沒查。
- 原因相同的阻擋。那個原因應該變成計畫審查席位執行的一條規則。
- 執行者回報成功、查驗卻不同意的那幾次。席位就是為了這種情況而存在。

做完這一步，才加入第二條流程或風險更高的動作。

## 導入時常見的錯誤

- **把規則寫在提示裡。** 執行環境不強制的指示，只是請求，不是控制。
- **為了省時間讓執行者自己查驗自己。** 在第一次出現假的「完成」之前，它確實省時間。
- **加了閘門卻不公開規則。** 執行者只能靠被退件來學規則。
- **把收據當成文書作業。** 如果沒有人讀收據，就別再產生沒人用的欄位，只留下能回答真實問題的那些。
- **讓代理調整管制自己的控制。** 見[控制面只有人能改](architecture.md#控制面只有人能改)。
