# 收據與稽核紀錄

> English: [../receipts-and-audit.md](../receipts-and-audit.md)

收據摘要工作執行中可供覆核的事件。它不是完整的安全控制，也不應成為秘密或敏感輸出的副本。

## 建議記錄欄位

- 工作單識別碼及版本、狀態、開始與結束時間。
- 請求、核准及執行身分的內部識別碼（依需要最小化）。
- 政策、模型、工具及執行環境版本。
- 工具呼叫摘要、核准事件、品質閘門結果及錯誤分類。
- 結果驗收狀態、人工覆核者、未解決事項與後續處置。
- 若採用雜湊，明確記錄演算法及被雜湊內容的範圍。

不得記錄明文憑證、私鑰、完整敏感提示、非必要個人資料或未經核准的客戶內容。日誌存取、保留、刪除及匯出須依適用政策管理。

## 完整性與限制

SHA-256 雜湊可用於檢查特定位元組內容是否與已知摘要相符；雜湊本身不是數位簽章，不能證明作者身分，也不能防止有權限者同時修改資料與摘要。數位簽章需有受控私鑰及驗證流程。所謂「附加式」或「僅追加」紀錄，取決於實作、權限與儲存設定，並非絕對不可竄改的保證。

重要紀錄可另外採取受限寫入、分離管理、備份、時間戳及定期核對等措施。若採用，應描述具體實作與剩餘風險，而非宣稱「絕對防竄改」。

## 每一次執行都留下收據

收據不是成功的獎勵。失敗的、被停下的、被取消的、沒通過閘門的工作，同樣要有一份紀錄作結，寫明停在哪裡、為什麼。否則事後能拿來研究的，只剩下順利的那幾次。

## 過程紀錄

除了結果，收據還應該讓覆核者能重建這件工作走過的路：

- 每一個審查席位在什麼時候做了什麼判定。
- 每一次被擋下或退回：被哪一道閘門、什麼原因、後來怎麼處理。
- 提出過的異樣，由誰處理、怎麼處理。
- 升級給人的事項，以及人回覆的決定。
- 若有放行：放行了什麼、什麼時候、放行後觀察到什麼。

用簡短的結構化條目記錄，不要寫成敘事。它的用途是：幾個月後不必靠任何人的記憶，也答得出「過程中發生了什麼」。

## 事故紀錄與重犯防護

執行者被閘門擋下或出錯時，要當場寫下事故紀錄：做了什麼、涉及哪一條規則或哪一道閘門、造成什麼後果、根因、如何修正。即使執行者認為是閘門判錯，也照寫，並在紀錄裡說明。一次誤擋，是關於那道閘門的資訊。

只是存起來的紀錄效果有限：同一個錯會在下一次工作中，由一個沒看過這份紀錄的執行者再犯一次。要讓紀錄發揮作用：

1. **附上可偵測的特徵。** 對每一筆紀錄問一句：機器可以找什麼，才能更早抓到同樣的錯？例如送審內容裡的某種樣式、少掉的某個步驟、不該出現的狀態。
2. **變成候選檢查。** 這個特徵成為一條提議的閘門規則，並附上一個應該被抓到的案例，和一個不應該被擋的案例。
3. **由人核准。** 代理可以提議，但不得自行裝上管制自己的規則（見[架構與治理原則](architecture.md#控制面只有人能改)）。
4. **其餘的要誠實標示。** 有些錯找不到可靠的特徵。把它們標成「僅供提醒」，不要假裝已經防住。

用這個方式衡量：事故紀錄的價值，是「不可能再發生第二次的錯誤」的數量。
